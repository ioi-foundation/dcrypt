# DCRYPT-2026-0005: sect283k1 validation permits a predictable ECDH-KEM secret

> Published as [GHSA-w3jf-cj7j-jmc5](https://github.com/ioi-foundation/dcrypt/security/advisories/GHSA-w3jf-cj7j-jmc5).
> `DCRYPT-2026-0005` remains the repository-local tracking identifier; consult
> the GHSA for the current CVE assignment status.

| Field | Value |
| --- | --- |
| Packages | `dcrypt-algorithms`, `dcrypt-kem` |
| Affected | Every published version from `0.9.0-beta.1` through `2.0.0` |
| Patched | `3.0.0` |
| Severity | High |
| CWE | CWE-1287: Improper Validation of Specified Type of Input |

## Impact

The removed `sect283k1` implementation used an incorrect subgroup-order
constant and accepted the on-curve point `(x, y) = (0, 1)` without the required
subgroup validation. That point has order two on this cofactor-four curve.

When an attacker supplied its compressed encoding to `EcdhB283k::decapsulate`,
an odd recipient secret produced the same public point with the known all-zero
x-coordinate, making the KDF input and derived KEM secret predictable. An even
recipient secret produced the identity and an observable error. The operation
therefore also disclosed secret-scalar parity. The accepted x-zero point could
trigger a panic when reserialized.

Applications that processed attacker-controlled B-283 keys or ciphertexts must
treat derived keys and protected data as potentially compromised and rotate the
corresponding long-term keys.

## Remediation

Version `3.0.0` removes the low-level `sect283k1` arithmetic, `EcdhB283k`, its
hybrid dimensions, and all associated public exports. The implementation was
not retained after the demonstrated flaw because repairing the constant and
one validation boundary would still require a fresh arithmetic and
constant-time review of a bespoke legacy binary-curve implementation.

## Workarounds

Stop accepting or generating dcrypt B-283 keys and ciphertexts. There is no
wire-compatible migration. Do not reinterpret existing encodings as another
curve. If immediate removal is impossible, place an independently reviewed
full SEC 1/NIST public-key validation boundary in front of every operation and
plan a key migration; the affected dcrypt implementation itself is not a safe
validator.

The detailed parameter comparison, artifact boundary, and preserved regression
fixture are documented in
[`V3-TRADITIONAL-EC-REMOVALS.md`](V3-TRADITIONAL-EC-REMOVALS.md).
