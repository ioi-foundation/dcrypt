# DCRYPT-2026-0008: Kyber implementation is not final FIPS 203 ML-KEM

> Drafted as [GHSA-xcw2-2p85-wmmp](https://github.com/ioi-foundation/dcrypt/security/advisories/GHSA-xcw2-2p85-wmmp).
> `DCRYPT-2026-0008` remains the repository-local tracking identifier; a CVE
> has been requested but not yet assigned.

| Field | Value |
| --- | --- |
| Package | `dcrypt-kem` |
| Affected | Every published version from `0.9.0-beta.1` through `2.0.0` |
| Patched | `3.0.0` |
| Severity | Moderate |
| CWE | CWE-327: Use of a Broken or Risky Cryptographic Algorithm |

## Impact

The affected `Kyber512`, `Kyber768`, and `Kyber1024` implementation does not
implement final FIPS 203 ML-KEM. The implementation itself was published from
`0.9.0-beta.1`; facade documentation began claiming FIPS 203 or forward
compatibility at `0.13.0-beta.1`, the stable `1.0.0` documentation claimed
complete or strict FIPS 203 adherence, and `2.0.0` presented the replacement
surface as a FIPS 203/ML-KEM API.

Among the confirmed differences, the implementation used a generic full
256-point cyclic transform and coefficient-wise multiplication instead of
ML-KEM's seven-layer NTT and degree-two base multiplication; derived key and
matrix material using a nonstandard seed/index flow; retained a pre-final
Kyber-style shared-secret and implicit-rejection construction rather than final
ML-KEM's `K` and `J(z || c)` functions; and accepted noncanonical or incoherent
key encodings without the required checks.

The result does not interoperate with final ML-KEM and cannot inherit FIPS 203's
conformance or the final algorithm's security analysis. No practical key
recovery attack against this implementation has been established, so this
advisory does not claim one. Applications must not treat the post-quantum
component of affected ciphertext or hybrid key establishment as a conforming
ML-KEM operation.

## Remediation

Version `3.0.0` replaces the former implementation with dcrypt-owned,
safe-Rust `MlKem512`, `MlKem768`, and `MlKem1024` implementations of final
FIPS 203. It enforces the distinct external encapsulation-key and internal
decapsulation-key decoding rules, final implicit rejection, the exact FIPS 203
encapsulation-key and decapsulation-key checks, caller-provided randomness, and
exact-size secret storage.

The release gate compares all 240 official ACVP cases exactly: 75 key-generation
cases, 75 deterministic encapsulation cases, 30 decapsulation cases, and 60
encapsulation/decapsulation-key validation cases. Independent tests exercise
all parameter sets and malformed boundaries. This project is not a
FIPS-validated cryptographic module.

## Workarounds

There is no compatibility flag that turns the affected format into final
ML-KEM. Stop creating new objects, retain provenance for legacy data, and
migrate keys and protocol framing to a supported standard implementation.
Applications using an affected hybrid construction must reassess the complete
combiner and classical component rather than assuming that an update
retroactively restores the post-quantum guarantee.
