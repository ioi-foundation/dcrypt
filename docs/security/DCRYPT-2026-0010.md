# DCRYPT-2026-0010: XChaCha20-Poly1305 APIs used a nonstandard construction

> `DCRYPT-2026-0010` is a repository-local identifier. A GHSA, CVE, or
> RustSec identifier has not yet been assigned.

| Field | Value |
| --- | --- |
| Packages | `dcrypt-algorithms`, `dcrypt-symmetric` |
| Affected | Every published version from `0.9.0-beta.1` through `1.2.3` |
| Replaced | `2.0.0` (withdrawn); supported replacement `3.0.0` |
| Severity | Moderate |
| CWE | CWE-327: Use of a Broken or Risky Cryptographic Algorithm |

## Impact

Every `dcrypt-algorithms` and `dcrypt-symmetric` release from
`0.9.0-beta.1` through `1.2.3` exposed a custom construction under the
`XChaCha20Poly1305` name. The `dcrypt` default/traditional facade was affected
transitively when it re-exported those exact-version dependencies. Instead of
deriving a subkey with HChaCha20 from the first 16 nonce bytes and forming the
IETF nonce as four zero bytes followed by the final eight nonce bytes, the
affected implementation derived a subkey from an ordinary IETF ChaCha20
counter-zero block using nonce bytes 0 through 11, then invoked
ChaCha20-Poly1305 with nonce bytes 12 through 23. This differs from the widely
deployed construction specified by the expired
`draft-irtf-cfrg-xchacha-03`.

This format does not interoperate with standard XChaCha20-Poly1305 and cannot
inherit the standard construction's analysis. The defect affects explicit-
nonce operations as well as the separately disclosed all-zero-nonce helpers.
No practical key-recovery or forgery attack attributable solely to the custom
subkey construction has been established, so this advisory does not claim one.
The demonstrated impact is standards failure and loss of the assurance callers
reasonably expected from the algorithm name.

The all-zero-nonce convenience operations additionally forced catastrophic
nonce reuse and are tracked separately as
[DCRYPT-2026-0009](DCRYPT-2026-0009.md).

## Remediation

Version `2.0.0` replaced the custom construction, but that release is withdrawn
and yanked for separate implementation-policy failures. Version `3.0.0` is the
first supported replacement. It implements standard XChaCha20-Poly1305 with a
dcrypt-owned, safe-Rust HChaCha20 core composed with the owned
ChaCha20-Poly1305 implementation, and requires an explicit 24-byte nonce for
every operation.

The release gate checks published HChaCha20 and XChaCha20-Poly1305 vectors and
an independent implementation outside the published dependency graph. The
standard API intentionally rejects legacy ciphertext instead of silently
reinterpreting it.

## Workarounds

Do not label ciphertext from an affected version as standard
XChaCha20-Poly1305 or expect it to interoperate with standard implementations.
Authenticate the provenance of legacy data, decrypt it only with the isolated,
non-published [migration tool](../../migration/legacy-xchacha20poly1305/README.md),
and re-encrypt trusted plaintext with unique nonces under the supported
construction. The migration tool is decrypt-only and does not add security to
historical ciphertext.
