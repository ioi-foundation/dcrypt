# DCRYPT-2026-0011: AES-GCM GHASH multiplication compiled with secret-dependent branches

> GitHub Security Advisory:
> [GHSA-86cg-f85f-5ggw](https://github.com/ioi-foundation/dcrypt/security/advisories/GHSA-86cg-f85f-5ggw).
> `DCRYPT-2026-0011` is the project's tracking identifier; it is not an
> assigned RustSec identifier.

| Field | Value |
| --- | --- |
| Packages | `dcrypt-algorithms`, `dcrypt-symmetric`, `dcrypt-pke` |
| Affected | Every published version from `0.9.0-beta.1` through `2.0.0` |
| Patched | `3.0.0` |
| Severity | Moderate |
| CWE | CWE-208: Observable Timing Discrepancy |

## Impact

The affected GHASH field multiplication tried to select each conditional XOR
with a byte mask computed by `0u8.wrapping_sub(bit_val)`. Optimizing Rust
compilers can recognize that selection and replace it with a conditional jump
that skips the XOR when the selected bit is zero.

The selected value is not always public. After the first GHASH block, the next
multiplicand is the previous accumulator XOR the next input block. The
accumulator depends on the secret hash subkey `H = AES_K(0)`, so the optimized
branch condition can depend on secret-derived state even when input lengths are
public. This contradicts the implementation's constant-time claim and creates
an observable timing discrepancy in AES-GCM authentication.

`dcrypt-algorithms` exposes the affected low-level `Gcm` operations.
`dcrypt-symmetric` builds its AES-128-GCM, AES-256-GCM, package, file, and
streaming operations on that implementation. `dcrypt-pke` uses the same GCM
implementation in its published P-384 and P-521 ECIES encryption and
decryption APIs. The root `dcrypt` crate is affected transitively when callers
enable and use the corresponding algorithms, symmetric, PKE, or full facade
features.

No practical recovery of the AES key or GHASH subkey, and no end-to-end
forgery, has been demonstrated from this compiler behavior. This advisory does
not claim either result. Exploitability depends on whether an attacker can
collect sufficiently precise repeated timing or execution-trace observations
for operations under the same key.

This issue is distinct from
[DCRYPT-2026-0003](DCRYPT-2026-0003.md), which concerns operation-nonce
handling and was technically remediated in withdrawn version `2.0.0`. The
GHASH compiler branch remains present in the published `2.0.0` artifact.

## Source and artifact provenance

The byte-mask loop entered repository history in commit
`26df4b5447d5839444aab63aab3c48069992262a` on 2025-05-12 and is contained by
source tags as early as `v0.7.0-pre`. The affected package range begins at
`0.9.0-beta.1`, the first published crates.io artifact for which the package
claim was verified; the earlier source tags do not widen the registry range.
The first `dcrypt-algorithms 0.9.0-beta.1` archive has crates.io SHA-256
`d43ddc3d263365597750d5c2507eed832a53da0273113b5d2046329f63712a63`
and records VCS commit `f308c73b62e304fa7d69880b403637de99308840`, which contains
the introducing commit.

Every one of the 25 published `dcrypt-algorithms` artifacts from
`0.9.0-beta.1` through `2.0.0` contains the byte-mask selection. The extracted
GHASH source has SHA-256
`71e85ada73e4291364947a9413dc6f9151294e2f71f356c28b1ca254eea67a18`
through `1.2.3` and
`1f2f3788b0eb63f168a1a4d12d9d0dcc9db21c620136fdd0e73ffd1d9a3324a0`
in `2.0.0`. The `dcrypt-algorithms 2.0.0` archive whose crates.io SHA-256 is
`6f5656352b0c47f82c0f534266f4b9404a519925833a6b6e540cf433b4a668d6`
records VCS commit `945e216c39ae3c8cb8c35d8401ceda32621887f8` and was compiled
directly with both of these optimizing toolchains:

- Rust 1.93.1, commit `01f6ddf7588f42ae2d7eb0a2f21d44e8e96674cf`,
  LLVM 21.1.8.
- Rust 1.96.0, commit `ac68faa20c58cbccd01ee7208bf3b6e93a7d7f96`,
  LLVM 22.1.2.

Both optimized outputs contain an input-bit `test` followed by a conditional
jump around the XOR attributed to the affected GHASH source. Every matching
published `dcrypt-symmetric` and `dcrypt-pke` artifact exact-pins
`dcrypt-algorithms` at the same version; all 25 PKE artifacts call `Gcm<Aes256>`
from their P-384 and P-521 ECIES paths. Downloaded archive hashes were required
to equal the crates.io API checksums before source inspection.

## Remediation

Version `3.0.0` replaces the byte-at-a-time selection with a fixed
128-iteration, whole-width `u128` masked multiplication. The release gate
compiles the exact release source with one generic codegen unit for
`x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`,
`wasm32-unknown-unknown`, and `thumbv7em-none-eabihf`. It requires exactly one
conditional branch bound to the fixed-counter loop backedge; no calls,
indirect/table control, or Thumb IT control in that loop; the reviewed
whole-width masks, field shifts, and reduction operations inside the loop; and
exactly five reviewed `u128` clearing calls on the normal post-loop path. The
default unwind build permits only the reviewed clearing calls and unreachable
`panic_in_cleanup` target as indirect x86 calls outside the loop.

The reviewed implementation is commit
`fd65ab2b4a84adbe7738b20efd69b3af1568d412`. It was integrated as commit
`304d2b553dbe4b25a45a5ebb44505ed49d7ccd93`; both commits resolve to the
byte-identical full tree
`dba67114f0e727e04cef46ba35bdc1a68aca425c`. The reviewed GHASH source
SHA-256 is
`ac74dafe22235346f40b40a2683151d2e653ec833246b556593afdd7b8b2f7a3`.
The fail-closed Python verifier and four-target shell driver at that commit have
SHA-256
`46ceb835b8c02246a0f52f311c550eefd7392ef47746da5c508b25a5c72dc7c8`
and `38fa8f6d3f492c8ee776a73e17600546217675394766a895d91b01b869619668`.

That compiler-shape gate is scoped to the recorded source, flags, compilers,
and targets. Functional NIST GCM vectors are checked separately; functional
vectors alone establish correctness, not constant-time compiler shape.

## Workarounds

There is no reliable source-level wrapper that prevents the affected compiler
transformation. Where the timing boundary is security-sensitive, stop using the
affected dcrypt AES-GCM and ECIES operations and migrate to an independently
reviewed implementation until upgrading to `3.0.0` or later. Preserve nonce
uniqueness during migration; changing implementations does not repair separate
damage caused by historical nonce reuse.
