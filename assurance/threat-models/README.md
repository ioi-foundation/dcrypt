# dcrypt threat-model control

This directory contains the candidate threat models for the exact atomic
assurance inventory bound by `../ledger.toml`. The models are risk and scope
records, not evidence that a mitigation works. Every current mitigation is
therefore either `planned` or `implemented-unverified`; no model or mitigation
has a passing verdict.

The coverage policy is deliberately conservative while 8,632 low-level rows
remain semantically unreviewed: every one of the 9,298 atomic rows is mapped to
all eleven mandatory threat classes. `coverage.json` preserves that exact
row-to-model mapping. Later semantic refinement may narrow a model only through
a reviewed change that keeps every row explicitly dispositioned.

Regenerate the exact coverage map and human-readable document with:

```text
python3 -B assurance/threat-models/generate-threat-models.py
```

Check the generated bytes without writing them with:

```text
python3 -B assurance/threat-models/generate-threat-models.py --check
```

Verify source bindings, schema, coverage, expiry, and generated artifacts with:

```text
python3 -B assurance/threat-models/verify-threat-models.py --mode ci
```

Run the deterministic adversarial fixtures without Cargo or network access:

```text
python3 -B assurance/threat-models/verify-threat-models.py --self-test
```

Release mode additionally rejects candidate or independently unreviewed models:

```text
python3 -B assurance/threat-models/verify-threat-models.py --mode release
```

An expired model, changed bound input, missing mandatory threat class, coverage
drift, unclassified atomic row, unsupported evidence claim, or mitigation marked
as verified without independently replayed passing evidence fails closed.
Release mode also requires exact independent-review evidence bindings, rejects
High or Critical residual risk, and rejects unresolved mitigation dispositions.

Evidence that completes a model review must use the closed
`threat-model-independent-review` kind and purpose and bind the exact model ID,
model-set version, applicability, subject commit/tree, artifact bytes, reviewer,
review date, validity date, and independent replay. Evidence that marks a
mitigation `verified` must instead use the closed
`threat-model-mitigation-verification` kind and purpose and additionally bind
the exact mitigation ID. Both evidence classes bind the canonical SHA-256 of
the exact individual `[[model]]` table and exactly one structured artifact with
the class-specific role; this avoids a whole-file hash cycle while invalidating
any model-field change. Evidence for another purpose, model, set version,
mitigation, or artifact role never satisfies either gate. Synthetic evidence
IDs, fixture identities, and artifact paths beneath fixture directories are
accepted only by the in-process adversarial self-test and are forbidden by
normal CI and release verification. The fixed `schema.toml` and
`threat-models.toml` inputs and all referenced/generated paths are inspected
lexically and must be ordinary files reached without any symlink component.
